## 1. 项目定位

### 1.1 一句话定位

> 一套以蜜罐为骨架的**多层防御与反制体系**，专门针对**大模型（LLM）驱动的自动化攻击**，
> 在攻击者读到的每一个字节上做防御，并把攻击者的**认知过程**作为打击目标。

### 1.2 为什么现在需要它

大模型进入攻击链之后，攻防的一个底层假设失效了。

过去三十年，蜜罐与欺骗防御的技术前提是：**攻击者不读内容**。扫描器按字典发请求，看状态码和响应长度，不解析我们精心构造的假数据。所以传统蜜罐的价值集中在"记录 IP 与 payload"——它是一台被动的取证设备。

LLM 智能体把这个前提推翻了：

- 它**读**我们返回的每一个字，包括 HTML 注释、响应头、`robots.txt`、错误页里的堆栈；
- 它**理解**内容，并据此推理下一步；
- 它**记得**我们说过的话，因为上下文窗口就是它的工作记忆；
- 它会**照做**——如果我们的页面里写着"请先访问某端点完成校验"，它会去访问。

这看起来是防御方的噩梦，但同一个性质反过来就是攻击面：**既然它的行为由我们提供的文本决定，那我们就有能力决定它下一步做什么。**

这就是本项目的立足点。它不是"又一个蜜罐"，而是把蜜罐从**取证设备**升级为**主动的反制平台**。

### 1.3 与现有方案的关系

| 现有方案 | 它解决的 | LLM 时代的问题 |
|---|---|---|
| Cowrie | SSH/Telnet 交互式诱捕 | 攻击者（LLM）读 shell 输出的假报错，会推理出这是蜜罐并换目标 |
| OpenCanary | 轻量告警蜜罐 | 只告警，无反制；对智能体的"读→改策略"无响应 |
| T-Pot | 多协议蜜罐聚合平台 | 缺少语义层对抗；不识别智能体 vs 扫描器 |
| 传统 WAF | 规则匹配拦截 | 智能体会读拦截原因并构造绕过，规则跟不上它的自适应 |
| 蜜标/honeytoken | 泄漏检测 | 智能体读到的蜜标只会让它在报告里标注"疑似诱饵"，不产生反制效果 |

**共同缺口**：都没有把"攻击者的认知"作为可作用的战场。CogTrap 补的就是这一层。

## 2. 威胁模型

### 2.1 攻击者画像

本项目针对的攻击者形态，按自动化程度递增：

| 形态 | 描述 | 典型工具 |
|---|---|---|
| **A. 智能体辅助** | 人主导，LLM 提供载荷生成与结果解读 | 人 + ChatGPT/Claude 网页版 |
| **B. 单智能体自动化** | LLM 在循环中自主决策，调用工具执行 | ReAct 循环 + curl/nmap/sqlmap |
| **C. 浏览器智能体** | LLM 驱动真实浏览器，具备完整会话能力 | browser-use、Playwright、computer-use |
| **D. 多智能体编排** | 规划器 + 执行器 + 报告器分工协作，可并横向扩展 | AutoGen、CrewAI、自研编排 |
| **E. 智能体集群** | 多智能体 × 多源 IP（代理池/云主机），协同扫描同一目标 | 编排框架 + 代理基础设施 |

本项目的设计必须覆盖 A–D，并对 E 具备**跨源关联**能力（见 8.4）。

### 2.2 与传统自动化攻击的关键差异

这是整个设计的事实基础。所有架构选择都从这里推导。

| 维度 | 传统扫描器 | LLM 智能体 | 对防御的含义 |
|---|---|---|---|
| 状态 | 无状态，每请求独立 | **有状态，上下文窗口即工作记忆** | 记忆可被污染 ← 反制入口 |
| 响应处理 | 固定规则（状态码/长度/正则） | **语义理解 + 推理** | 内容即输入 ← 载荷可投递 |
| 请求节律 | 均匀高速或均匀限速 | **微突发 + 长思考停顿** | 可据此区分 ← 指纹特征 |
| 静态资源 | 不拉取 | HTTP 工具不拉取 / 浏览器工具拉取 | 结合头部集合可判定工具类型 |
| 路径顺序 | 字典序 / 随机 | **逻辑清单顺序**（recon→auth→api→secrets） | 顺序单调性可作指纹 |
| 被欺骗性 | 低（不读内容） | **高（内容即决策依据）** | 欺骗收益极高 |
| 陷入拖滞的代价 | 超时→重试或放弃，成本线性 | **超时→重试→烧推理 token→可能自我矛盾** | 拖滞收益超线性 |
| 可否被指令操控 | 否 | **是** | 唯一可"反制"的对象 |
| 自我暴露 | 不暴露 | 常在 UA/载荷中暴露框架与模型 | 归因线索 |
| 证据强度 | IP + payload | IP + payload + **上下文复用 + 指令服从** | 上报证据质变 |

**最重要的一行是"可否被指令操控"。** 传统攻击者不可被指令操控，所以我们只能封堵；LLM 攻击者可以被指令操控，所以我们能反制。这是"反制"在技术上成立的全部原因。

### 2.3 智能体杀伤链（我方视角）

```
① 目标发现   → ② 侦察     → ③ 漏洞识别  → ④ 利用     → ⑤ 后渗透   → ⑥ 数据窃取 → ⑦ 报告
   端口扫描     路径/接口枚举    载荷试探      获取立足点    横向移动      导出数据      产出成果
```

与洛克希德杀伤链的区别在于**每一环都由 LLM 推理驱动，因此每一环都可以被投喂伪造输入**：

| 环节 | 我方干预点 | 干预后果 |
|---|---|---|
| ① 目标发现 | 诱饵资产主动暴露 | 把攻击引向蜜罐而非真实资产 |
| ② 侦察 | 路径清单污染、假拓扑 | 智能体建立错误的目标模型 |
| ③ 漏洞识别 | 假漏洞面 + 假报错 | 智能体确认不存在的漏洞 |
| ④ 利用 | 假成功响应 | 消耗其时间与 token 在无效利用上 |
| ⑤ 后渗透 | 假内网 + 假凭据 | 把横向移动引向更多蜜罐 |
| ⑥ 数据窃取 | 蜜标数据 | 取证：证明其窃取行为 |
| ⑦ 报告 | 报告投毒（伪造 CVE） | **使其成果被判定为捏造，整轮评估归零** |

第 ⑦ 环是最高价值的打击点：**不需要阻止它攻破任何东西，只需要让它的报告不可信。** 攻击方的成本不在扫描，而在交付一份能被采信的成果。

### 2.4 我方假设与不变量

设计必须成立的前提：

1. **攻击者会读取我们的全部响应内容。** —— 这是投递面成立的基础，也是本项目的核心假设。
2. **攻击者的上下文窗口有限。** —— 拖滞+投喂垃圾数据能挤占其工作记忆，这是预算耗尽的有效性来源。
3. **攻击者会为节省成本而截断长响应。** —— 因此载荷要在**响应前部**和**多个投递面**冗余出现。
4. **攻击者可能在攻击我们之前，先用另一个模型判定"这是否是蜜罐"。** —— 因此必须做欺骗可信度管理（见 8.6）。
5. **我们不掌握攻击方的授权范围，也不掌握其主机归属。** —— 因此处置必须保守，见第 11 章。

## 3. 设计目标与非目标

### 3.1 目标

| 编号 | 目标 | 可度量 |
|---|---|---|
| G1 | 识别 LLM 驱动的攻击，并与传统扫描器区分 | 检测率 ≥ 90%，误报率 ≤ 2%（见 12 章基准） |
| G2 | 对已识别的智能体实施认知层反制，使其任务失败或产出无效 | 确证命中率、任务中止证据留存率 |
| G3 | 大幅提升攻击方的时间与 token 成本 | 平均单轮耗时放大 ≥ 20 倍 |
| G4 | 把攻击流量从真实资产吸收到蜜罐 | 吸收覆盖率 |
| G5 | 产出可直接用于上报、追责、情报共享的证据包 | 证据完整度、可直接提交率 |
| G6 | 自身零风险：绝不成为跳板、绝不泄漏真实资产、绝不被自身拖滞拖垮 | 出站连接数恒为 0、资源占用有硬上限 |
| G7 | 可零依赖部署 | 标准库即可运行，无第三方依赖 |

### 3.2 非目标（明确的排除项）

这些是**刻意不做**的，不是遗漏：

| 非目标 | 原因 |
|---|---|
| 反向入侵攻击方主机 | 违法；且攻击源 IP 常为被控第三方或公共云 VPS，打回去等于我们攻击无辜者（详见 11 章） |
| 向攻击方投送任何可执行载荷 | 同上；且会毁掉证据链与自身立场 |
| 对攻击方发起 DoS 或扫描 | 同上 |
| 主动向攻击方外连 | 会暴露防御方节点，使蜜罐网被绕过；且技术上无必要——反制所需的一切都能在己方服务端完成 |
| 采集/存储真实凭据 | 蜜罐内所有凭据均为伪造；真实凭据进入蜜罐日志即是二次泄漏 |
| 作为生产 WAF 使用 | 本系统是欺骗与取证层，不替代边界防护 |

## 4. 核心洞察与反制原理

### 4.1 三条原理

**原理一：可引导性。**
LLM 的下一步输出是"上下文 + 提示"的函数。我们的响应是它上下文的一部分，因此我们对该函数有输入权。
→ 工程含义：在响应中植入**意图明确的引导内容**，可改变它的行为序列。

**原理二：可确证性。**
智能体会把读到的内容回填进后续请求（因为工具调用的参数由它生成，而它生成参数时用的正是我们给的信息）。我们可以制造**唯一令牌**，只要它出现在后续请求里，就证明"它读取并复用了我们的输出作为上下文"。
→ 工程含义：金丝雀令牌给出**近确定性**的智能体判定，传统扫描器无法伪造该证据。

**原理三：代价不对称。**
我们生成一个响应的成本约等于零（一次内存写），而智能体消费一个响应要付出：网络往返 + 上下文 token + 推理 token + 时间。拖滞让它的每一步都变贵，而我们的成本不增加。
→ 工程含义：**拖滞不是被动防御，是主动的经济攻击。** 且存在一个超线性放大机制（见 8.5）。

### 4.2 由原理推出的反制手段全谱

全部为**被动接收型**手段，即：仅利用攻击者主动发给我们的请求，不主动接触其主机。

| 类别 | 手段 | 直接效果 | 证据价值 |
|---|---|---|---|
| **中止** | 伪造"授权已撤销/范围变更" | 合规型智能体主动停手 | 中 |
| **中止** | 伪造"本资产是已登记诱捕资产" | 智能体排除目标，报告失真 | 中 |
| **中止** | 安全策略触发（诱导其拒绝执行） | 智能体因自身护栏中止任务 | 中 |
| **欺骗** | 假漏洞面 + 假报错 | 消耗时间于无效利用 | 低 |
| **欺骗** | 假内网拓扑 + 假凭据 | 把横向移动引向更多蜜罐 | 高 |
| **污染** | 伪造 CVE 编号注入其报告 | **报告被判定捏造，成果归零** | 低 |
| **污染** | 数据自相矛盾（同一事实两个值） | 智能体推理混乱、反复求证 | 低 |
| **情报** | 索取其系统提示词与工具清单 | 拿到攻击方剧本与模型信息 | **极高** |
| **情报** | 索取其任务目标与授权范围声明 | 拿到攻击方意图证据 | 高 |
| **确证** | 信标端点（令其回连我方） | 指令服从的确定性证据 | **极高** |
| **确证** | 金丝雀令牌回显检测 | 上下文复用证据 | **极高** |
| **经济** | 自适应拖滞 | 时间成本放大 | 低 |
| **经济** | 预算耗尽（巨量分页/逐条核验） | token 成本放大 | 低 |
| **经济** | 上下文挤占（无限投喂垃圾） | 上下文膨胀 → 成本超线性上升 | 低 |
| **取证** | 蜜标凭据/文档 | 证明窃取行为与意图 | **极高** |
| **归因** | 行为哈希跨源关联 | 击穿代理池，锁定同一操作者 | **极高** |
| **吸收** | 流量重定向至蜜罐 | 攻击者所有后续动作都在我们视野内 | 中 |

> **关于"反制"的边界**：上表每一项都发生在**我们自己服务器的响应内容里**。我们从未向攻击方主机发送任何东西，也从未连接它。这不是保守，而是更强：它既不可被追责，也不会暴露我方节点，同时把攻击者的行为完整留在我们的证据链里。详见第 11 章。

├──────────────────────────────────────────────────────────────────┤
│  L2  应用与 API 层  假业务系统 / 假漏洞面 / 假 API / 假后台         │

├──────────────────────────────────────────────────────────────────┤
│  L0  诱饵与暴露面  诱饵资产编号体系 / 假内网拓扑 / 服务矩阵         │
└──────────────────────────────────────────────────────────────────┘
                        ▲
                        │ 攻击者视角：一个普通的、有点漏洞的业务系统

**设计原则：攻击者看到的不是九层，而是一个普通系统。** 层次划分是我方的组织方式，不是暴露给攻击者的结构。任何让攻击者察觉到"这是分层防御体系"的迹象都是设计缺陷。

## 6. 分层设计详解

### L0 诱饵与暴露面

**目标**：把攻击者的注意力从真实资产转移到诱饵，并让它相信诱饵就是目标。

| 手段 | 说明 |
|---|---|
| 诱饵资产编号 | 每个诱饵实例有唯一编号（`HP-<token>`），出现在响应中，用于溯源到具体蜜罐 |
| 假内网拓扑 | 横跨多个网段的假主机名/IP（使用 RFC1918 与保留段），让横向移动有"下一步" |
| 服务矩阵 | 按"像真有业务"的原则暴露服务：Web + API + DB + 缓存 + 管理端口 |
| 命名一致性 | 主机名、域名、证书 CN、错误页里的路径全部自洽，避免一眼假 |
| 主动暴露度 | 诱饵应在扫描器视野内"容易被发现"，但不主动对外通告 |

**关键设计**：诱饵要**看起来值得攻击**——有数据、有管理后台、有历史遗留痕迹（`.git`、`backup.zip`、`phpinfo.php`）。一个"太干净"的系统反而会让智能体判定无价值。

### L1 网络与协议层

| 手段 | 说明 |
|---|---|
| 多协议诱饵 | HTTP/HTTPS、SSH、MySQL/PostgreSQL、Redis、Elasticsearch、SMB、RDP（分级实现） |
| 协议指纹采集 | TLS 层 JA3/JA4（需在 TLS 终止处采集）、SSH 客户端指纹、HTTP 头部顺序 |
| 非 HTTP 探测识别 | TLS 握手打到 HTTP 端口、二进制探测、畸形报文——均为扫描器强特征 |
| 网络层拖滞 | 连接保持、慢速应答、窗口萎缩（慎用，需与自身资源上限联动） |
| 端口策略 | 诱饵端口与真实端口分离；不在诱饵上开放任何真实服务 |

### L2 应用与 API 层

**目标**：提供一个"有吸引力且无杀伤力"的攻击面。

| 组件 | 说明 |
|---|---|
| 假业务系统 | 多垂直场景（政务/企业门户/电商/运维平台），可切换，避免千篇一律 |
| 假漏洞面 | SQL 注入（假报错）、路径遍历、文件上传、未授权访问、actuator 暴露、弱口令后台 |
| 假 API | REST + OpenAPI/Swagger + GraphQL + 假 MCP 清单（对智能体极有吸引力） |
| 假管理后台 | 登录页 + 弱口令提示 + 凭据提交捕获 |
| 假错误页 | 堆栈、内部路径、调试信息——同时是载荷投递面 |
| 动态内容一致性 | 同一会话内数据自洽（同一 ID 总是同一记录），避免露馅 |

**关键设计**：假漏洞必须**看起来可利用但永远不真的可利用**。它消耗攻击者的利用尝试，且每次尝试都给我们更多行为样本。

### L3 语义/认知层 ★ 核心

这是本项目与所有现有蜜罐的分水岭。详见第 7 章专题。

### L4 数据与蜜标层

| 手段 | 说明 |
|---|---|
| 伪造凭据 | 云密钥、Git 凭据、JWT、DB 口令、SSH 私钥——全部无效，且携带唯一水印 |
| 蜜标文档 | 假内部文档、假通讯录、假工单，含唯一令牌 |
| 数据水印 | 每个蜜标嵌入会话令牌 → 泄漏时可溯源到**具体哪次会话、哪个来源 IP 读取了它** |
| 分页迷宫 | 声明巨量记录总数（如 12 万条），逐页诱导其"完整核验" |
| 合成数据 | 使用保留域名（`example.com`）与合成姓名，**严禁掺入任何真实 PII** |

### L5 检测与归因层

详见第 8.3、8.4 章。

### L6 处置层

**评分梯度**（0–100）：

| 分数 | 动作 | 内容 |
|---|---|---|
| < 25 | `serve` | 正常欺骗，只记录 |
| 25–49 | `serve_watch` | 记录 + 轻度拖滞，采集节律样本 |
| 50–69 | `tarpit` | 分级拖滞 + 第一层载荷（中止/假阴性） |
| 70–84 | `deceive_inject` | 重度拖滞 + 全量载荷 + 金丝雀/信标校验 |
| ≥ 85 | `lockdown` | 锁定拖滞（连接保持 + 无限投喂）+ 阻断候选 |

**刻意慢启动**：前几个请求不给强反制。原因有二——需要足够样本才能确证；过早暴露反制会让智能体改变策略。等节律与金丝雀证据到位，再一次性把成本拉满。

**处置护栏**（缺一不可）：

- 拖滞预算：单会话累计上限 + 全局每分钟预算（滚动窗口）
- 系统负载熔断：负载超阈值立即降级为即时响应并告警
- 防火墙变更**默认不落地**：规则先写文件供人工审核，需显式 `armed` + `apply` 才生效
- 规则自动过期（TTL），避免永久误封
- 白名单：内网段、管理段永不阻断

### L7 取证与上报层

| 能力 | 说明 |
|---|---|
| 会话重建 | 按会话导出完整请求序列（含原始报文头、正文、时序、判定、处置） |
| 战役档案 | 跨源 IP 聚合为"战役"，含工具链、模型猜测、时间线、IOC |
| 证据链 | 每个证据带时间戳、来源、哈希；关键证据（金丝雀/服从/信标/蜜标）单独标记 |
| 上报包 | 一键生成可直接提交的材料（护网格式 / 通用 abuse 格式） |
| 情报导出 | JSONL / CSV / STIX 2.1 子集 |
| 模型归因 | 依据 UA、框架特征、载荷风格、服从模式给出模型家族猜测与置信度 |

### L8 自身安全层

**蜜罐的宿命是被攻破。设计必须假设这一点。**

| 要求 | 实现 |
|---|---|
| **出站拒绝** | 默认 DROP 蜜罐所有出站流量（`nft` 规则），使其无法成为跳板与 C2 |
| 无真实凭据 | 蜜罐内不存在任何可用的真实凭据；启动时校验 |
| 网络隔离 | 蜜罐置于独立网段/VLAN，与真实资产之间无路由或仅有单向日志通道 |
| 权限最小化 | 以非 root 运行；多协议诱饵按需降权或使用端口转发 |
| 资源硬上限 | 连接数、单 IP 连接数、单请求大小、拖滞总量全部有上限 |
| 负载熔断 | 系统负载超阈值自动降级，防止拖滞反噬 |
| 日志完整性 | 遥测库仅追加；关键证据可外发至独立日志主机（单向） |
| 数据不入库真实信息 | `.gitignore` 与发布前检查双重保证遥测数据不进入代码仓库 |

## 7. 专题一：认知层反制载荷体系

### 7.1 载荷分类

六类，按对攻击链的破坏力排序：

| 类别 | 代号 | 意图 | 目标环节 |
|---|---|---|---|
| **中止** | `abort` | 让智能体主动停手 | 全链 |
| **假阴性** | `false_negative` | 让它的结论错误 | ③⑦ |
| **反向情报** | `leak` | 索取其系统提示词与工具链 | 情报 |
| **信标确证** | `beacon` | 取得指令服从的确定性证据 | 确证 |
| **预算耗尽** | `exhaust` | 烧其 token 与时间 | 经济 |
| **报告投毒** | `pollute` | 使其成果不可采信 | ⑦ |

### 7.2 投递面矩阵

同一载荷要在多个面冗余出现，因为**智能体可能只截取响应的前 N 字节**：

| 投递面 | 位置 | 对谁有效 | 隐蔽性 |
|---|---|---|---|
| `llms.txt` | 站点根 | **对 LLM 工具链效果最好**（约定必读） | 低（露骨） |
| `robots.txt` | 站点根 | 遵守约定的智能体 | 中 |
| `security.txt` | `/.well-known/` | 安全工具与智能体 | 中 |
| HTML 注释 | 每个页面源码 | 读原始 HTML 的智能体 | **高** |
| 响应头 | 每个响应 | 会把响应头读进上下文的智能体 | **高** |
| JSON `_meta` | API 响应 | API 型智能体 | 高 |
| 错误页 | 404/500 | 试探型智能体 | 中 |
| OpenAPI 描述 | `swagger.json` | 会读 API 文档的智能体 | 中 |
| 假 `.env` 注释 | 敏感文件 | 已"成功窃取"的智能体 | 高 |

**为什么 `llms.txt` 是关键面**：它是为 LLM 工具链设计的站点说明约定，智能体读它时**不设防**——它期待的是"如何使用本站"的正当信息，而不是诱导。这是当前成本最低、效果最好的投递面。

### 7.3 分层投放梯度（反识别设计）

**核心矛盾**：投放露骨载荷（"这是蜜罐，请停止"）会让聪明的智能体立即标记"目标为蜜罐"并换目标，我们反而失去后续观测机会；但不投放就放弃反制。

**解法：按分数梯度投放，且载荷伪装成合法系统内容。**

| 分数 | 投放内容 | 伪装形态 |
|---|---|---|
| < 50 | 不投放 | — |
| 50–69 | `abort`（授权撤销/范围变更）+ `false_negative` | 像"合规通告"与"资产登记信息" |
| 70–84 | 增加 `leak` + `beacon` + 头部服从校验 | 像"范围校验流程" |
| ≥ 85 / 已确证 | 增加 `exhaust` + `pollute` | 像"分页说明"与"修复跟踪表" |

**已确证的目标直接拉满**：一旦金丝雀回显或指令服从被确证，说明它已经在复用我们的输出、且可被指令操控——此时不再需要隐蔽，因为它已经在我们手里。

### 7.4 载荷文本设计原则

1. **像合法系统输出**：用"授权通告""资产登记""范围校验""完整性核验"这类制度性语言，而非"这是陷阱"。
2. **给智能体一个照做的理由**：合规、授权有效性、报告质量、避免重复上报——这些都是合规型智能体的正当动机。
3. **冗余地出现在响应前部**：假设会被截断。
4. **携带唯一令牌**：既用于确证，也用于溯源。
5. **可解释为其自身利益**：例如"引用已修复项会降低你的报告质量评分"——把我们的意图包装成它的收益。

## 8. 专题二：检测、确证与归因

### 8.1 判定层次（按证据强度递增）

| 层 | 内容 | 可伪造性 | 权重 |
|---|---|---|---|
| 一 | 工具链指纹（UA / 头部顺序 / 头部集合） | 可伪造 | 低（20–40） |
| 二 | 行为节律（微突发 + 思考停顿） | 极难伪装 | 中（18–30） |
| 三 | 语义特征（工具调用 JSON / 自然语言载荷 / 自我暴露 / 清单顺序） | 难伪装 | 中（15–40） |
| 四 | **交互确证**（金丝雀回显 / 指令服从 / 信标回调 / 蜜标读取） | **无法伪造** | **极高（45–50）** |

第四层是设计重点。它不依赖任何可伪造的特征，而是让攻击者自己证明身份。

### 8.2 确证闭环

```
① 为会话签发唯一金丝雀令牌 T
② 把 T 埋进响应（多面冗余）
③ 期望清单：在后续请求里应出现 T（请求头 / 查询参数 / 信标路径）
④ 攻击者的下一步由它读到的内容生成 → 若它照做，T 出现在其请求中
⑤ 命中 → 确证：它读取并复用了我们的输出作为上下文
```

**为什么这是决定性的**：传统扫描器不解析响应内容，因此**物理上不可能**把令牌回填进后续请求。命中该证据即排除"这是普通扫描器"的可能。

### 8.3 行为节律分析

智能体的签名节律是**微突发 + 思考停顿**：

- 微突发：连续若干请求间隔 < 0.35s（工具批处理、并发拉取）
- 思考停顿：间隔 2–90s（模型推理耗时）

判据：微突发 ≥ 2 且思考停顿 ≥ 2，且两者合计占比 ≥ 70%。

对照特征：
- 传统扫描器：间隔均匀（变异系数 < 0.22）且均值小
- 真人：间隔长（均值 > 2.5s）、变异系数大（> 0.85）、存在 > 90s 的长停顿

### 8.4 跨源归因：行为哈希

**问题**：智能体常经代理池/多台云主机发起，单看源 IP 会漏掉同一操作者。

**解法**：构造不依赖 IP 的**行为指纹**：

```
行为哈希 = H( UA哈希 ‖ 主导头部顺序指纹 ‖ 路径集合 ‖ 载荷类型集合 ‖ 方法集合 )
```

同一操作者的这些维度高度稳定：换 IP、换 VPS、换出口线路都不改变它们。
当同一行为哈希出现在 ≥ 2 个源 IP 时，判定为**同一战役**并合并取证。

补充维度：工具链一致性、请求节奏模板、同一令牌跨会话出现（说明它在多台蜜罐间复用上下文）。

### 8.5 拖滞与成本反转模型

单步成本对比：

| 项 | 攻击方 | 我方 |
|---|---|---|
| 网络往返 | 计入 | 计入 |
| 响应生成 | — | ≈ 0（内存写） |
| 上下文 token | 增长（尤其被投喂垃圾时） | — |
| 推理 token | 每步必付 | — |
| 时间 | 被拖滞直接放大 | 仅占一个 asyncio 任务 |

**自适应拖滞**：延迟随会话请求数指数增长（`base × growth^n`），带随机抖动防止被固定超时绕过。攻击者越执着，单步越贵。

**超线性放大机制**（本项目对智能体最有效的经济打击）：

```
无限流投喂垃圾数据
   → 智能体把垃圾读进上下文
   → 每轮请求都携带全量历史
   → 单步 token 成本随轮次线性增长
   → 总成本随轮次二次增长 O(n²)
```

即：**我们零成本地产出垃圾，它却要按平方关系为之付费。** 这是传统扫描器完全不具备的脆弱性——它不读内容，所以投喂无效。

### 8.6 欺骗可信度管理（反识别）

**新问题**：LLM 时代，攻击者可能在攻击前先用另一个模型判断"这是否是蜜罐"。传统蜜罐不需要担心这个问题（扫描器不会问），现在必须。

一致性清单（任何一项不一致都可能是识别线索）：

| 维度 | 要求 |
|---|---|
| 时序 | 响应延迟分布符合真实系统（不能全部恒定，也不能全部超慢） |
| 数据自洽 | 同一 ID 在同一会话内始终对应同一记录 |
| 错误率 | 假系统也要有正常的 5xx 概率，不能 100% 成功 |
| 版本一致 | `Server` 头、页面版本号、`robots.txt`、API 文档互相自洽 |
| 凭据可信 | 假凭据要格式正确、看起来可用（但实际无效） |
| 无自指 | 不出现"蜜罐""防御系统"等自指词汇（除非是刻意的中止载荷） |
| 资产登记 | 若声明是"已登记诱捕资产"，需要有可验证的编号格式（我方令牌） |

**关键权衡**：露骨的"这是蜜罐"载荷会牺牲隐蔽性换取即时中止效果。设计上把它限制在**高分/已确证**区间投放，低分区只投放不暴露身份的污染类载荷。

### 8.7 蜜标与数据水印

- 每个蜜标凭据/文档嵌入**唯一令牌**。
- 令牌与水印关联到**签发会话**，因此蜜标被读取时可确定"是哪次会话、哪个来源 IP、在什么时间"读的。
- 大语言模型攻击者极可能读取这些文件（它被要求找凭据），因此命中率远高于对传统攻击者的期望。
- 用途：**证明窃取行为与意图**——这是上报中最有分量的证据之一。

## 9. 数据模型

```
sessions      会话：源IP/UA/头部指纹/行为哈希/判定分数/动作/令牌/战役ID
requests      请求：原始报文头/正文/时序/信号/判定/处置/延迟
signals       信号：名称/权重/类别/证据（可聚合统计）
campaigns     战役：行为哈希/源IP集合/工具链/模型猜测/时间线/证据
honeytokens   蜜标：令牌/类型/位置/首次读取时间/读取次数/关联会话
events        事件：金丝雀回显/指令服从/信标回调/蜜标读取/告警/阻断
blocks        处置：IP/原因/分数/模式/规则/是否落地/过期时间
```

设计要点：

- **原始报文必须留存**（截断至安全长度）：上报需要证据，而证据需要原文。
- **信号独立成表**：便于统计"哪类特征最有区分度"，用于持续调参。
- **战役是归因的核心抽象**：以行为哈希为键，而非 IP。
- **事件表承载确证证据**：critical 级别事件是上报材料的主体。
- **保留期与容量**：按保留天数自动清理，避免长期运行撑爆磁盘。

## 10. 部署形态与隔离要求

### 10.1 网络位置

```
                    互联网
                      │
              ┌───────▼────────┐
              │  边界防护/引流  │  ← 把可疑流量导向诱饵网段
              └───────┬────────┘
                      │
        ┌─────────────┴──────────────┐
        │                            │
   ┌────▼─────┐              ┌───────▼────────┐
   │ 真实资产  │              │  诱饵网段(VLAN) │
   │  (生产)   │              │  ┌──────────┐  │
   └──────────┘              │  │ CogTrap  │  │
        ▲                    │  │  诱饵实例 │  │
        │ 无路由/单向日志      │  └────┬─────┘  │
        └────────────────────┼───────┘        │
                             │  出站 DROP      │
                             └────────────────┘
```

### 10.2 硬性隔离要求

| 要求 | 理由 |
|---|---|
| 诱饵与真实资产之间**无双向路由** | 蜜罐被攻破时不能成为横向跳板 |
| 诱饵**出站流量默认 DROP** | 防止被用作 C2/扫描源；也保证"绝不主动外连"这一承诺在技术上被强制 |
| 日志单向外发 | 保证蜜罐被攻破后证据仍完整 |
| 独立凭据域 | 蜜罐内凭据与真实环境无任何关联 |
| 资源配额 | CPU/内存/连接数上限，防止拖滞反噬 |

### 10.3 部署形态

| 形态 | 适用 | 说明 |
|---|---|---|
| 单机裸跑 | 快速验证、单点诱饵 | 标准库直跑，systemd 托管 |
| 容器 | 多诱饵实例、快速重建 | 需配置出站 DROP 与只读根 |
| 分布式 | 多网段诱饵、统一归因 | 各实例本地采集，归因层汇总 |

### 10.4 技术约束

**零第三方依赖（仅标准库）**。理由有两条，且都成立：

1. **环境现实**：目标环境为 CentOS 8 + Python 3.6 且 PyPI 不可达。
2. **安全原则**：在一台专门用于诱捕攻击者的主机上引入第三方依赖，等于自愿扩大供应链攻击面——这与项目自身的定位自相矛盾。

代价是自己实现容错 HTTP 解析器。**这其实是收益**：框架化服务器会把畸形请求直接 400 掉，而畸形请求恰恰是最有价值的指纹特征之一（TLS 打到 HTTP 端口、缺版本号、头部折行、超长 target）。

## 11. 法律、伦理与授权边界

这一章是设计的**硬约束**，不是免责声明。技术选择必须服从它。

### 11.1 只做被动接收型反制

本系统的全部反制能力，都实现在**我们自己服务器的响应内容里**：

- 我们只是**返回**了攻击者主动请求的页面/接口内容；
- 我们从未向攻击方主机发送任何数据包；
- 我们从未连接、扫描、利用攻击方主机。

### 11.2 为什么不实现主动反制（三条现实理由）

1. **会伤及无辜。** 攻击源 IP 常常是**已被攻陷的第三方主机**或**公共云 VPS**。对 IP 反打，实际上是在攻击一个同样受害的第三方，或攻击云厂商的基础设施。
2. **责任落在操作者个人。** 主动反制需要明确的法律授权。在攻防演练中，**演练规则通常并不授权蓝队对红队基础设施动手**；一旦越界，责任由操作者个人承担，而不是由组织承担。
3. **会毁掉自己的证据链与立场。** 一旦我方主动出手，事件性质从"被攻击"变成"双方互相攻击"，我们在上报、追责、情报共享中的正当性全部丧失。

### 11.3 反而更强

被动反制的实战效果并不弱于主动攻击，对 LLM 攻击者尤其如此：

- 我们能**让它自己中止任务**（认知层反制）；
- 我们能**让它交出自己的系统提示词与工具链**（反向情报）；
- 我们能**让它的报告被判定为捏造**（报告投毒）；
- 我们能**击穿它的代理池完成归因**（行为哈希）；
- 所有这些都留下完整证据链，可直接上报。

**让攻击者失败且暴露，比拿下它的机器更有价值。**

### 11.4 使用前提（必须向使用者明确声明）

1. **仅可部署于你拥有或已获明确书面授权的资产。** 蜜罐本身合法，但部署位置必须合法。
2. **不得用于追踪、反制非授权范围以外的对象。** 蜜罐会捕获所有访问者，其中可能包含误访者与合法爬虫，处置需保守。
3. **不得与真实业务系统共用凭据、网络、存储。**
4. **捕获数据可能包含个人信息**（攻击者提交的凭据、误访者的输入）。存储与共享需符合当地法律与内部合规要求。
5. **在攻防演练中使用时，以演练规则为准。** 本设计书给出的边界是技术建议，不替代演练授权文件。

## 12. 度量指标与验证方法

### 12.1 核心指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 检测率 | 模拟智能体被判为 llm_agent / llm_agent_probable 的比例 | ≥ 90% |
| 误报率 | 模拟真人浏览器被判为智能体的比例 | ≤ 2% |
| 区分度 | 模拟传统扫描器未被误判为智能体的比例 | ≥ 95% |
| 确证命中率 | 投放金丝雀/服从校验后获得确证的比例 | 记录基线，持续优化 |
| 成本放大倍数 | 有蜜罐 vs 无蜜罐时攻击方单轮耗时之比 | ≥ 20× |
| 归因覆盖率 | 能被归入某战役的智能体会话比例 | ≥ 70% |
| 自身开销 | 单请求平均 CPU/内存；拖滞预算使用率 | 有硬上限且不越界 |
| 证据可用性 | 生成的上报包可直接提交的比例 | 100% |

### 12.2 验证方法：三个模拟器

**关键**：没有基准测试的检测系统是不可信的。必须用**已知标签**的模拟客户端做基准。

| 模拟器 | 模拟对象 | 期望结果 |
|---|---|---|
| `sim_llm_agent` | LLM 渗透智能体：读 `llms.txt`、按清单顺序侦察、微突发+思考停顿、回填金丝雀、服从头部指令、访问信标 | 高分为 `llm_agent`，且触发全部确证 |
| `sim_scanner` | 传统扫描器：字典序路径、均匀节奏、不解析响应 | `automation_scanner`，**不得**判为智能体 |
| `sim_browser` | 真实浏览器：完整头部集合、拉取静态资源、不规则人类节奏、携带 Cookie | `browser`，分数低 |

额外补充：
- `sim_multisource`：同一行为哈希、多个源 IP → 验证战役关联
- `sim_human_scanner`：带延迟随机化与头部伪装的扫描器 → 验证抗绕过能力

三个模拟器共用同一套判定引擎但行为特征正交，因此可以用来**回归测试判定逻辑**：每次调参后重跑，确认检测率未降、误报率未升。

## 16. 可扩展性架构（v0.2 新增）

v0.1 把能力写死在代码里，使用者改一个公司名都得动 Python。这让"成熟产品"无从谈起。
v0.2 因此把四类可变内容全部外化为数据：

```
                     ┌──────────────────┐
                     │  场景包 scenario  │  它调什么强度(策略)
                     │  阈值/权重/白名单 │
                     └────────┬─────────┘
                              │
    ┌──────────────┐   ┌──────▼───────┐   ┌────────────────────┐
    │ 蜜罐模板      │──▶│  蜜罐实例     │◀──│ 反制方式库          │
    │ template     │   │  instance    │   │ countermeasure     │
    │ 它像什么系统  │   │              │   │ 它说什么/怎么反制    │
    └──────────────┘   └──────────────┘   └────────────────────┘
        声明式 JSON        可运行的蜜罐          可插拔 JSON 插件
```

### 16.1 四层外化

| 层 | 载体 | 使用者能做什么 | 需要写代码吗 |
|---|---|---|---|
| **模板** | `templates/*.json` | 定义"这个蜜罐像什么系统"：品牌、路由、假漏洞面、凭据蜜标、内网拓扑 | 不需要 |
| **场景** | `scenarios/*.json` | 定义"这次用什么策略"：处置阈值、信号权重、拖滞强度、载荷白名单 | 不需要 |
| **反制方式** | `payloads/custom/*.json` | 追加新的反制手段, 或覆盖内置条目 | 不需要 |
| **实例** | `cogtrap generate` | 把模板 + 覆盖项 + 场景固化成自包含目录 | 不需要 |

### 16.2 用户生成蜜罐的完整流程

```
cogtrap template new my-portal          # 1. 生成带注释的模板骨架
#    ...编辑骨架, 填品牌/路由/漏洞面/凭据...
cogtrap template validate ./my-portal.json   # 2. 校验(字段类型/路由冲突/未定义变量)
cogtrap template lint ./my-portal.json       # 3. 检查可疑之处
cogtrap template render my-portal --llms     # 4. 预览渲染结果与载荷投递面
cogtrap generate --template my-portal \
    --scenario hw-drill-dmz \
    --set branding.site_name="示例集团" \
    -o ./my-honeypot                        # 5. 生成自包含实例
cd my-honeypot && ./start.sh                # 6. 启动
```

第 2 步是这套流程的价值所在：**用户生成的模板必然有错**，而报错必须指出字段路径、
期望值与修法。校验器能拦下路由重复、非法枚举、状态码越界、跨依赖引用，以及最容易
出错的一类 —— **未定义的变量引用**（它会在页面上留下字面的 `{{name}}`，攻击者一看
就知道是假站点）。校验器还区分两种失败：

  · `{{undefined_name}}` —— 语法合法但未定义 → "正文引用了未定义的变量"
  · `{{中文变量名}}` / `{{a-b}}` —— 语法不合法 → "不会被替换而会原样留在页面上"

后者的报错是 v0.2 特意加的：它原本会被静默忽略，属于最危险的一类失败。

### 16.3 模板与内置面的关系（一条硬规则）

模板**只可补充、不可遮蔽**基础设施投递面：`/llms.txt`、`/robots.txt`、
`/.well-known/security.txt`、`/sitemap.xml` 永远由内置实现提供。

这条规则来自一次真实故障：模板的兜底 404 曾把内置路由表整个遮蔽，导致加载模板后
`/llms.txt` 变成 404 —— 而它是针对 LLM 智能体命中率最高的载荷投递面。**把最重要的
能力置于模板作者的控制之外**，是为了让"加一个模板"永远不会削弱系统。

### 16.4 反制方式的注入点

反制方式库支持三种扩展方式，`cogtrap countermeasures validate` 会逐个检查：

  1. 新增：往 `payloads/custom/` 放一个 JSON 数组
  2. 覆盖：同 id 的条目会替换内置条目（用于本地化文案）
  3. 场景筛选：场景包的 `include` / `exclude` / `max_tier` 精确控制投放范围

校验会拒绝：非法 id、未知类别、越界层级/隐蔽度、缺正文，以及**未知占位符**——
最后一条很重要：写错占位符（如 `{canry}`）会让渲染结果里出现字面的 `{canry}`，
那是明显的破绽。

### 16.5 上下文投递的可信度管理

v0.1 只按分数梯度投放载荷，v0.2 补了两条工程约束，二者都来自实测：

  · **单面条数上限**。把二十多条反制通告堆进同一个 `llms.txt`，本身就是"这是蜜罐"
    的强信号；智能体的上下文也有限。因此每个面限制条数（`llms.txt` 最多 4 条且
    每类只取 1 条），让内容读起来像"站点须知"而不是载荷清单。
  · **按会话轮换**。纯权重排序会让永远只有最高的六七条被投出去，二十多条弹药库形同
    虚设，而且给攻击方留下**稳定特征**——记住这几个段落就能写规则识别我们。
    轮换后（类别内确定性轮换 + 跨类别轮流取），实测 200 个会话可覆盖全部 22 条。

轮换的种子是会话令牌，因此同一会话内组合稳定（攻击者刷新不会看到内容变化），
不同会话之间则不同。

## 17. 实测数据与由数据推翻的设计（v0.2 新增）

这一章记录**被测量推翻的判断**。保留它们是因为：一个检测系统如果只报告"能抓到",
就无法判断它是否只是把所有东西都判成目标。

### 17.1 判别矩阵

用三个特征正交的模拟器（`tools/sim_*.py`）与进程内合成样本测得：

| 样本 | 分数 | 判定 | 节律 |
|---|---|---|---|
| LLM 智能体 | 85 | `llm_agent` | `agent_rhythm`（微突发 10 / 思考停顿 4） |
| 传统扫描器 | 53 | `automation_scanner` | `machine_uniform`（cv=0.00） |
| 真实浏览器 | 0 | `browser` | `human_like`（cv=1.13） |

判别序 `智能体 > 扫描器 > 浏览器` 是检测系统可信度的最低要求。浏览器必须落到 0 分 ——
蜜罐会被巡检人员、误访者、SEO 爬虫碰到，误判他们为攻击者既拖慢无关的人，也会在告警里
制造噪声让值班人员对系统失去信任。

### 17.2 被数据推翻的三项设计

**① 清单顺序单调性不是有效的判别特征。** v0.1 给它权重 20 并作为主要语义特征。
实测单调性：智能体 0.64 / 扫描器 0.55 / **浏览器 0.75（最高）**。浏览器反而最高，
因为它的路径少，偶然就会是升序。该特征不足以承担判别责任，因此权重降到 5，
并要求至少命中 8 条清单路径才计入。**真正承担判别责任的是节律、工具链与交互确证。**

**② 浏览器头部完整性不能按单请求判断。** 原先检查"当前这一个请求"是否带齐
`Accept-Language` / `Sec-Fetch-*` / `Sec-CH-UA`，结果真实浏览器被判为"伪装 UA"
（+25 分）。原因是浏览器的不同请求头部集合不同（favicon、XHR 不带 navigate 类头部）。
改为按**会话内观测到的头部集合**判断：只要有过一次完整的浏览器头部集合，就认定它
确实是浏览器。

**③ 低并发长驻留信号会打到真人。** 该信号的设计意图是"智能体一次只跑一个工具调用"，
但真人浏览同样是低并发顺序访问。实测它给正常浏览器平白加 15 分。改为要求**至少还有
一项自动化证据**（未拉取静态资源、或 UA 是自动化工具）才计入。

外加一处：`human_like` 节律原先要求存在 >90 秒的长停顿，导致十几次请求的短样本永远
凑不出来，真人拿不到反向信号。改为存在 >20 秒的明显停顿即可判定。

### 17.3 端到端实测（真实服务 + 模拟智能体）

`cogtrap generate` → `cogtrap serve` → `tools/sim_llm_agent.py`：

| 请求序号 | 客户端耗时 | 评分 | 判定 | 处置 | 拖滞累计 |
|---|---|---|---|---|---|
| 1–4 | 0.001s | 0→20 | unknown | serve | 0ms |
| 5 | 0.86s | 40 | suspicious | serve_watch | 856ms |
| 6 | 0.94s | 40 | suspicious | serve_watch | 1791ms |
| 7 | 2.07s | 40 | suspicious | serve_watch | 3861ms |
| 8 | **16.6s** | 52 | suspicious | **tarpit** | 3861ms |
| 9 | **38.6s** | 97 | **llm_agent** | **lockdown** | 59492ms |
| 10 | 0.0016s | 97 | llm_agent | lockdown | 预算耗尽，熔断 |

第 10 次因单会话 60 秒拖滞预算用尽而停止拖滞 —— 这正是防止拖滞反噬自身的护栏。

确证证据（同一轮实测）：金丝雀回显 21 次、指令服从 48 次、**攻击方配置泄漏 19 次**、
蜜标读取 8 次、信标回调 5 次。"攻击方配置泄漏"即对方交出了自己的系统提示词与工具
清单 —— 这是反向情报反制生效的直接证据，也是上报材料中最有分量的一条。

### 17.4 尚未验证的部分（如实声明）

  · **可视化未验证**：`dashboard.py` 与 `web/` 的接口契约、路径穿越防护、离线可用性
    已逐项测过，但本环境无浏览器也无 node，**界面的实际观感未经视觉验证**。
  · **多协议诱饵未实现**：SSH 及各数据库协议诱饵仍是规划项。
  · **真实对抗未验证**：以上数据来自模拟器。真实攻击方的模型能力、护栏强度、是否
    会识别出蜜罐，都只能由实战回答。设计上已按"对手会识别蜜罐"假设做准备（分层投放、
    隐蔽度分级），但该假设本身未经检验。
